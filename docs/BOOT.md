# ProsenjitOS boot architecture

ProsenjitOS uses one versioned kernel handoff contract with multiple boot producers. The native BIOS loader is the primary implemented path. Multiboot2/GRUB remains a compatibility and development adapter; a native UEFI loader is still pending.

## Native legacy BIOS path

`BIOS -> native stage-1 -> native stage-2 -> Boot Protocol v1 handoff -> kernel`

- Stage 1 is a 512-byte BIOS boot sector and loads the fixed 24-sector stage-2 region using INT 13h EDD.
- Stage 2 collects and validates the E820 memory map, constructs the bounded Boot Protocol v1 handoff at physical `0x6000`, and reserves that allocation in the memory map.
- Stage 2 loads the flat kernel image from the fixed native image layout in bounded 32 KiB chunks through an E820-validated low-memory bounce buffer, copying each chunk to the validated 1 MiB destination.
- The producer preserves the BIOS drive identity and validates the EDD 3.0 device path and AH=48 geometry before advertising the supported legacy ISA/ATA path.
- The kernel dispatches the v1 magic through `kernel/boot_protocol.c`, validates the handoff before PMM initialization, and reserves the kernel, handoff, modules, copied RSDP and framebuffer ranges as applicable.

The current native image layout generated by `scripts/build.sh` is:

`LBA 0`: stage 1 (512-byte boot sector)

`LBA 1..24`: stage 2

`LBA 25 onward`: build-sized flat kernel image

`LBA 2046..2047`: reserved two-sector crash-record extent

`LBA 2048..2559`: disposable ProsenjitFS test partition

The build checks that the kernel extent does not overlap the reserved crash-record sectors and that formatting the test partition preserves them.

## Boot Protocol v1

The shared ABI is defined in `include/abi/boot.h`; the kernel parser is in `kernel/boot_protocol.c`.

The parser validates, among other invariants:

- magic, version, header size, total allocation bounds and reserved fields;
- bounded, aligned, non-overlapping memory-map, module and boot-device descriptor regions;
- checked physical ranges against the CPU-derived MAXPHYADDR limit;
- sorted, non-overlapping memory-map entries and reserved ownership of the handoff and payload ranges;
- module type/flags, pairwise physical aliasing and overlap with the handoff, framebuffer and ACPI RSDP;
- framebuffer bounds and exclusion from allocator-usable RAM;
- copied ACPI RSDP signature, revision, length and checksums through the dedicated validator.

The native BIOS producer currently rejects malformed or ambiguously overlapping E820 input rather than silently accepting an unsafe map. The PMM remains limited to its established 1 GiB managed/identity-mapped window; describing higher RAM in the handoff does not make it allocatable.

The kernel retains a separate Multiboot2 compatibility path. Multiboot2 data is not silently reinterpreted as a native v1 payload.

## Native boot-device discovery and storage boundary

The BIOS stage-2 loader validates the EDD 3.0 ATA device-path metadata and carries the returned capacity and logical-sector geometry in the opaque v1 device descriptor. The kernel compares that geometry with ATA IDENTIFY before enabling the native legacy PIO storage path.

This resolver is intentionally narrow: supported legacy ISA/ATA channel layouts only. PCI/ATAPI, USB, SCSI, RAID, NVMe, UEFI device paths and non-standard legacy port layouts require their own transport/resolver implementations. If EDD metadata or the ATA IDENTIFY cross-check fails, native ATA storage initialization fails closed.

The bootloader itself does not parse MBR/GPT or depend on a filesystem. Partition and filesystem discovery belong to the kernel storage layer.

## Crash-record persistence boundary

The native BIOS storage path reserves LBAs 2046–2047 and attaches the panic writer only after EDD/ATA geometry, ATA identity, cache-flush support and partition-reservation checks succeed. The fatal exception path uses the bounded raw ATA writer; it does not route panic I/O through normal block-device or health-report callbacks.

The isolated QEMU test deliberately triggers the production `ud2` / vector-6 fatal path, verifies the ATA sector write+flush, then starts a second QEMU process on the same retained image and verifies that the production reader recovers sequence 1 / vector 6. The reserved sectors are compared byte-for-byte across the second boot.

This is QEMU success-path evidence. It does **not** prove physical-media durability, real hardware ATA behavior, actual power-loss behavior or torn-sector recovery under physical interruption.

## GRUB and other traditional bootloaders

GRUB is not part of the native boot dependency. The Multiboot2 path remains a compatibility/development adapter. Any future external loader adapter must produce the documented kernel handoff contract rather than introducing a second kernel memory-manager ABI.

## Future UEFI path

UEFI will be another producer of the same Boot Protocol v1 handoff:

`UEFI firmware -> ProsenjitOS EFI loader -> Boot Protocol v1 -> kernel`

UEFI filesystem/ESP access, GPT installation handling, memory-map acquisition, ExitBootServices sequencing, loaded-image validation and device-path capture belong in the EFI loader. The kernel must receive normalized handoff data and must not depend on firmware boot services after the handoff. No native UEFI loader is implemented yet.

## Remaining boot limitations

- The native BIOS image uses a fixed LBA layout and legacy BIOS INT 13h EDD reads.
- The BIOS device resolver currently supports only validated legacy ISA/ATA PIO layouts.
- Native UEFI loader and UEFI boot-device discovery are pending.
- Kernel/module descriptor ranges are validated, but payload cryptographic signature verification and measured boot are not implemented.
- The current PMM manages only its established 1 GiB mapped window.
- Secure Boot, signed kernel/module admission, measured boot and rollback protection remain future hardening work.
