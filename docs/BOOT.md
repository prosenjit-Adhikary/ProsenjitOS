# ProsenjitOS boot architecture

ProsenjitOS uses a native boot path as the primary design target while keeping the existing Multiboot2/GRUB path as a compatibility and development fallback.

## Native BIOS path

The current native prototype is deliberately independent of MBR/GPT partition parsing and filesystem discovery:

`BIOS -> native stage-1 -> native stage-2 -> flat kernel image -> kernel`

- stage-1 is exactly one 512-byte BIOS boot sector
- stage-1 loads a fixed, reserved stage-2 area
- stage-2 collects the firmware E820 memory map
- stage-2 converts that map into a Multiboot2-compatible in-memory structure
- stage-2 loads the kernel from a fixed LBA layout and copies it to the kernel's linked address
- the native boot magic tells the kernel that the handoff came from the ProsenjitOS bootloader
- the kernel keeps its existing Multiboot2 memory-map parser, so the native path does not need a second memory-manager ABI

The native disk layout generated by `scripts/build.sh` is currently:

`LBA 0 -> stage-1 (one 512-byte BIOS boot sector)`
`LBA 1..24 -> stage-2 (24 reserved sectors)`
`LBA 25..(25 + kernel_sectors - 1) -> flat ProsenjitOS kernel image`
`LBA 2046..2047 -> reserved two-sector crash-record extent`
`LBA 2048..2559 -> disposable ProsenjitFS test partition`

The kernel extent is build-derived; the build rejects any kernel image that
reaches or overlaps the crash-record reservation. It also validates the
crash-record extent against the ProsenjitFS partition and disk-image bounds,
checks the MBR partition descriptor, and verifies that formatting the
ProsenjitFS test volume preserves the reserved crash-record sectors. The
reservation is part of the native disk-image layout contract, but it is
**not yet attached to a production block device**: crash records are not
therefore guaranteed to be persisted by normal kernel operation. Do not
interpret the reservation as proof of a working crash-recovery path.

The stage-1 loader reads exactly 24 sectors; stage-2 enforces the same
24-sector bound. Stage-2 reads at most 64 sectors (32 KiB) per BIOS request
into an E820-validated bounce buffer, copies each chunk to the E820-validated
1 MiB destination in protected mode, and returns to real mode for the next
BIOS request. Each range must be covered by one enabled usable-memory entry;
overlapping reserved or disabled E820 entries reject the range even when a
broader usable entry also covers it. Firmware records are accepted only at
the defined 20-byte legacy or 24-byte extended sizes; partial extensions fail
closed.

This is an **early bootloader prototype**, not the final storage-installation format.

## Why partition tables are not required at this stage

A BIOS firmware can execute a boot sector without ProsenjitOS first implementing MBR/GPT partition discovery. The native prototype therefore keeps partitioning below the bootloader boundary.

Later storage support can add:

`BIOS/UEFI -> bootloader -> partition discovery -> filesystem -> VFS`

without changing the kernel/bootloader contract.

For removable media and installed disks, the project will still retain MBR and GPT support in the storage layer because those formats are needed for broad disk-layout compatibility. They are **not prerequisites for the native boot protocol itself**.

## GRUB and other traditional bootloaders

GRUB is not part of the native boot dependency. The repository continues to build a Multiboot2/GRUB ISO so the existing development and compatibility path remains available.

The intended long-term relationship is:

- **Primary:** ProsenjitOS native bootloader
- **Compatibility:** Multiboot2/GRUB or another external bootloader
- **Kernel:** one kernel image with a small boot-handoff boundary

A traditional bootloader therefore does not need to be statically linked into the kernel. It should provide the documented handoff contract and transfer control to the same kernel entry path.

## Future UEFI path

UEFI support will be added as another boot protocol implementation rather than forcing GPT parsing into the kernel entry path:

`UEFI firmware -> ProsenjitOS EFI loader -> common boot handoff -> kernel`

GPT/ESP handling belongs to the UEFI installation/storage tooling. The kernel should receive normalized boot information instead of depending on a particular firmware or partition format.

## Important limitations of the current native prototype

- The native BIOS loader uses a fixed LBA layout.
- The prototype currently uses BIOS INT 13h extensions for disk reads.
- The native BIOS loader reads the kernel in bounded 32 KiB chunks through an E820-validated low-memory bounce buffer, copying each chunk to the E820-validated 1 MiB destination before reusing the buffer.
- No filesystem or partition parsing is performed by the native bootloader yet.
- Real SATA/NVMe/USB device-driver support remains a later kernel/driver milestone.
- Secure Boot, signed kernel verification, measured boot and rollback protection are future hardening milestones.

The fixed-layout prototype is intentional: it proves that ProsenjitOS can boot through its own loader without requiring GRUB, while leaving MBR/GPT/filesystem complexity in the later storage stack.
